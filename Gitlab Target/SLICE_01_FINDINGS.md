## FINDING-01: `remote_id`-based object-storage adoption bypasses the local-path allowlist and depends on unverified ownership binding

**Invariant:** an object-storage reference adopted into a GitLab model must be one the current upload flow itself created — no client-supplied identifier should let a request "adopt" storage content it didn't legitimately just upload.

**Entry point:** any Workhorse-accelerated, direct-upload-to-object-storage endpoint whose Grape params include `file.remote_id` — concretely, `POST /api/v4/projects/import` and `POST /api/v4/projects/import-relation` (`lib/api/project_import.rb:97,308`: `optional 'file.remote_id', type: String, desc: '...(generated by Workhorse)'`), and by the same mechanism, any other endpoint using the shared `FileUploadHelpers`/`workhorse_authorize` pattern (avatar upload, package uploads, etc., per [SYSTEM_CONTEXT.md §6](SYSTEM_CONTEXT.md)).

**Attacker-controlled input:** the value of the `file.remote_id` (and `file.path`, `file.name`, etc.) multipart field, as received by Grape.

**Exact call chain:**
```
Grape endpoint (e.g. lib/api/project_import.rb) declares `optional 'file.remote_id'`
  → params['file'] reaches lib/gitlab/middleware/multipart.rb only if the
    HTTP_GITLAB_WORKHORSE_MULTIPART_FIELDS env key is present (Workhorse-set)
  → Gitlab::Middleware::Multipart::Handler#open_file
      → UploadedFile.from_params(params, allowed_paths)   [lib/uploaded_file.rb:53]
          remote_id.present? → file_path = nil            [lib/uploaded_file.rb:59-60]
          (the File.realpath + allowed_path? branch at lines 62-66 is skipped entirely)
  → the resulting UploadedFile (remote_id set, no local path) is later passed into
    ObjectStorage::Concern#cache!                          [app/uploaders/object_storage.rb:499]
      new_file.remote_id.present? → cache_remote_file!(new_file.remote_id, ...)  [line 502-503]
  → cache_remote_file!(remote_object_id, original_filename)  [app/uploaders/object_storage.rb:552]
      branch A: ObjectStorage::PendingDirectUpload.exists?(storage_location_identifier, remote_object_id)
                → file_path = with_bucket_prefix(remote_object_id)      [line 556, NO cleanpath/prefix re-check]
      branch B: else → file_path = File.join(TMP_UPLOAD_PATH, remote_object_id)
                → Pathname.new(file_path).cleanpath.to_s
                → raise unless file_path.start_with?(TMP_UPLOAD_PATH + '/')  [lines 558-560]
```

**Security boundary:** the boundary between "storage object the current request's own upload flow legitimately created" and "storage object that exists anywhere in this GitLab instance's bucket." Branch B enforces this boundary with a canonicalize+prefix check that constrains the result to a shared `TMP_UPLOAD_PATH` *namespace*, not to *this specific upload*. Branch A enforces it only via an existence lookup (`.exists?`) whose SQL/lookup semantics (composite-key equality vs. anything looser) I did not confirm by reading the `PendingDirectUpload` class body (a Grep for its class definition inside `object_storage.rb` returned no match, meaning it is likely defined in a separate file not in this sparse checkout — a concrete gap in this pass, not a finding of absence).

**Broken assumption:** that a `remote_id` reaching `cache_remote_file!` was necessarily generated by Workhorse for *this specific* upload transaction. The code that checks it (`.exists?`) only proves the identifier is *some* real, currently-pending upload in the same storage location — not that it belongs to the current user, project, or request.

**Expected behavior:** a `remote_id` should only ever resolve to storage content created by the same upload authorization it is being redeemed against (e.g., bound to a nonce/model/user tied at `workhorse_authorize` time and re-checked at `cache_remote_file!` time).

**Actual behavior (as read):** branch B is scoped to a shared temp namespace, not to a specific request. Branch A's scoping depends entirely on `PendingDirectUpload.exists?`'s exact semantics, which I could not verify in this pass.

**Required preconditions:** (a) the attacker must submit a `remote_id` value directly to a Grape endpoint that declares it as an optional param — normally this value is only ever populated by Workhorse's JWT-signed rewrite, so the attacker would need either (i) a way to reach Rails/Puma without the request having passed through Workhorse's `Multipart` middleware, or (ii) knowledge of another user's own legitimately-issued, still-pending `remote_id` (a two-part token containing `SecureRandom.hex`/a UUID-derived SHA256 hash — not practically guessable, but potentially observable via a side channel not evaluated here, e.g. logs, error messages, or a race between two of the attacker's own concurrent uploads if IDs are ever reused/predictable). Neither precondition was confirmed or ruled out in this pass.

**Potential impact:** if a precondition above holds, an attacker could cause GitLab to adopt object-storage content belonging to a different in-flight upload as their own project-import file (or other Workhorse-accelerated upload target) — an object/upload confusion (BOLA-flavored) issue, not a directory-traversal-to-arbitrary-file-outside-the-bucket issue, since both branches constrain the result to the instance's own object-storage bucket in some form.

**Confidence:** Low-Medium. This is a real, source-confirmed architectural gap (I1 does not apply to the `remote_id` branch, exactly as [SYSTEM_CONTEXT.md §16](SYSTEM_CONTEXT.md) flagged as an open question), but I could not confirm either required precondition, and one full check (`PendingDirectUpload.exists?`'s exact semantics) is unverified because its class body is outside this sparse checkout.

**Exact source locations:** `lib/uploaded_file.rb:53-67`; `app/uploaders/object_storage.rb:499-507` and `:552-579`; `lib/api/project_import.rb:97,308`.

**Why the issue is exploitable (if preconditions hold):** because the code path that would normally provide the missing guarantee (I1's realpath+allowlist check) is unconditionally skipped the moment `remote_id.present?` is true, with no code anywhere in this call chain re-establishing "this remote_id was issued to this request" as a substitute guarantee for branch A.

## FINDING-02: The Workhorse-JWT trust boundary is a network-topology assumption, not a framework-enforced one

**Invariant:** `params['file']['path']`/`['remote_id']`/etc. can only be populated by Workhorse's signed multipart rewrite, never directly by an HTTP client.

**Entry point:** every Grape endpoint that declares `optional 'file.path'`/`'file.remote_id'` (found at minimum in `lib/api/project_import.rb`; the broader set across all Workhorse-accelerated upload endpoints was not separately enumerated in this pass).

**Attacker-controlled input:** the raw multipart body of a request that reaches the Rails/Puma process without first passing through gitlab-workhorse's `Multipart` middleware.

**Exact call chain:**
```
Client → (assumed: Workhorse reverse proxy, workhorse/internal/upstream/routes.go
          matches this route to `mimeMultipartUploader`/`tempfileMultipartProxy`,
          rewrites file parts, signs a JWT into HTTP_GITLAB_WORKHORSE_MULTIPART_FIELDS)
       → (if this hop is ever skipped) Puma/Rails directly
       → Grape parameter binding (`optional 'file.remote_id'`) accepts whatever
         string the client put in that multipart field, verbatim
       → lib/gitlab/middleware/multipart.rb#call:
             encoded_message = env.delete(RACK_ENV_KEY)
             return @app.call(env) if encoded_message.blank?    # <-- no-op if header absent
       → UploadedFile.from_params receives the raw, client-supplied params hash
         exactly as if it had come from Workhorse
```

**Security boundary:** whether an HTTP request can reach the Rails application server directly, bypassing gitlab-workhorse. This is a **deployment/network-topology property**, not something enforced in the code read in this pass — `Gitlab::Middleware::Multipart#call` simply does nothing (`return @app.call(env)`) if the Workhorse header is absent; it does not reject the request or refuse to process `params['file']` from an un-rewritten body.

**Broken assumption:** that "the only way to reach this Grape action is through Workhorse" is true for every deployment topology and every future change to it, forever. Nothing in `lib/api/project_import.rb`, `UploadedFile`, or the `Multipart` middleware itself verifies that the specific request was proxied through Workhorse — the guarantee is entirely extrinsic (firewalling / not exposing the Puma port).

**Expected behavior:** ideally, a value like `remote_id` that is supposed to only ever originate from a trusted internal component would carry its own proof of that origin (e.g., itself be inside the Workhorse JWT envelope, or be re-validated against a server-side-only record at the point of use) independent of network placement.

**Actual behavior:** correctness depends on the reverse-proxy topology alone; `cache_remote_file!`'s own checks (Finding 1) are the only *code-level* backstop if that topology assumption ever fails for a given deployment (custom Kubernetes ingress misconfiguration, a container port exposed for debugging, a future refactor that adds a new Grape endpoint accepting `file.remote_id` behind a Workhorse route whose matcher was written slightly too broadly, per the same class of bug documented in [SECURITY_INVARIANTS.md INV-11](SECURITY_INVARIANTS.md)).

**Required preconditions:** a deployment or request-routing condition where Rails/Puma is reachable without the request first being processed by gitlab-workhorse's `Multipart` middleware — not confirmed possible or impossible on a standard Omnibus/Helm install in this pass (this is fundamentally a deployment-configuration question, better answered by testing against a real instance/network topology than by further source reading).

**Potential impact:** if the precondition holds, this removes Workhorse from the trust chain entirely for this parameter, collapsing this finding into Finding 1's impact (object confusion within the object-storage bucket) with a much lower attacker-effort bar (no guessing required — the attacker supplies `remote_id` directly).

**Confidence:** Low as an independently exploitable issue (it is fundamentally conditional on a deployment/topology question I could not evaluate from source alone) — but Medium as an architectural observation, since it is precisely the kind of "one enforcement point that every caller must remember to rely on" pattern that has recurred repeatedly elsewhere in this codebase's history ([SECURITY_INVARIANTS.md](SECURITY_INVARIANTS.md), cross-entry pattern in [PATCH_ARCHAEOLOGY.md](PATCH_ARCHAEOLOGY.md)).

**Exact source locations:** `lib/gitlab/middleware/multipart.rb:174-179` (`Handler#call`); `lib/api/project_import.rb:89-98,300-309`.

**Why the issue is exploitable (if the precondition holds):** because nothing downstream of the missing Workhorse hop re-derives or re-checks that the request was actually proxied — the absence of the signed header simply causes the middleware to pass the request through unchanged, not to reject it.

## FINDING-03: The Rack-level path-traversal middleware cannot see request bodies or 12 specific parameter names, by design

**Invariant:** every attacker-reachable representation of a path-shaped value is checked for traversal sequences before being used in a file operation.

**Entry point:** any current or future feature that constructs a filesystem/repository path from a POST/PUT JSON or form body field — especially one named `content`, `description`, `body`, or `note` — where that specific endpoint does not *also* call `Gitlab::PathTraversal.check_path_traversal!` itself.

**Attacker-controlled input:** any body-carried parameter value.

**Exact call chain (of the gap itself, not of a confirmed exploit):**
```
lib/gitlab/middleware/path_traversal_check.rb#call
  → path_traversal_attempt?(request, log_params)
      original_fullpath = request.filtered_path
      exclude_query_parameters(request)          # strips EXCLUDED_QUERY_PARAM_NAMES from GET params only
      decoded_fullpath = CGI.unescape(request.fullpath)   # <-- URL path + query string ONLY, never request.body
      Gitlab::PathTraversal.path_traversal?(decoded_fullpath, match_new_line: false)
```

**Security boundary:** "any request-supplied value that could become a filesystem path is inspected somewhere before use" — this middleware is one of three enforcement mechanisms for that boundary ([SECURITY_INVARIANTS.md INV-02](SECURITY_INVARIANTS.md)), and it is the one most likely to be assumed complete because it runs unconditionally in front of the whole app.

**Broken assumption:** that a perimeter, request-level check is a meaningful backstop for *every* endpoint. It is not — it structurally cannot see anything in a request body, and it structurally cannot see the 12 named parameters even in the query string.

**Expected behavior:** either the middleware inspects the body too, or every endpoint that could plausibly build a path from a body field independently calls `check_path_traversal!` (as `UploaderFinder` correctly does, per I2 above).

**Actual behavior:** confirmed by direct read — the middleware's scope is exactly `request.fullpath`, and the 12-name exemption list is unconditional.

**Required preconditions:** the existence of a feature that (a) accepts one of the 12 exempted names, or any body field at all, and (b) uses that value in a file-path-shaped operation without its own independent `check_path_traversal!` call. **I did not find such a feature in this pass** — the confirmed upload/download call sites I traced (`UploadsActions#show`, `UploaderFinder`, `ObjectStorage::Concern#retrieve_from_store!`) all call the helper directly, independent of this middleware. This finding is therefore a **documented architectural gap with no confirmed live sink** in the file-upload/download slice specifically — it is recorded here because it is the single most reusable "if a new feature is ever added carelessly, this is the exact shape of the resulting bug" fact in this slice, not because a current instance of it was located.

**Potential impact:** if such a feature exists or is later added, unauthenticated-reachable request-body-based path traversal in whatever file operation that feature performs.

**Confidence:** Medium on the architectural gap being real (directly read, not inferred); Low on any current exploitable instance existing (none found).

**Exact source locations:** `lib/gitlab/middleware/path_traversal_check.rb:6-22` (`EXCLUDED_QUERY_PARAM_NAMES`, `PATH_TRAVERSAL_MESSAGE`), `:54-72` (`path_traversal_attempt?`, note `request.fullpath`/`request.GET` only, never `request.body`/`request.POST` in this specific check — though `exclude_query_parameters` does call `request.GET`, and note also that Rails re-reads `request.body` separately from `fullpath` entirely, so nothing here inspects it).

**Why the issue is exploitable (if a sink exists):** the middleware would silently pass the request through (`return @app.call(env) unless path_traversal_attempt?(...)`), and if the target endpoint has no independent check, nothing in the request pipeline would ever reject the payload.

## FINDING-04: `config/routes/uploads.rb` applies a materially looser filename constraint to the appearance/branding upload route than to every sibling upload route

**Invariant:** every route serving a stored upload by filename constrains that filename identically, since they all dispatch to the same `UploadsController#show`.

**Entry point:** `GET /uploads/-/system/:model/:mounted_as/:id/:filename` where `model` matches `appearance` (GitLab instance branding: favicon, logo, header logo, PWA icon) — this route is reachable **unauthenticated**, since instance branding assets must render on the pre-login pages.

**Attacker-controlled input:** the `:filename` route segment.

**Exact call chain:**
```
config/routes/uploads.rb:24-27
  get "-/system/:model/:mounted_as/:id/:filename", to: "uploads#show",
      constraints: { model: /appearance/, mounted_as: /logo|header_logo|pwa_icon|favicon/, filename: /.+/ }
                                                                                              ^^^^^^^^^^^^
                                                        (contrast with the SAME route pattern at lines 4-11,
                                                         14-16, 19-21, 40-43, 46-48, all of which use
                                                         filename: %r{[^/]+}  — i.e. no slash allowed at all)
  → UploadsController#show → UploadsActions#show   [app/controllers/concerns/uploads_actions.rb:49]
      Gitlab::PathTraversal.check_path_traversal!(filename_param)   # still runs, regardless of route looseness
```

**Security boundary:** the routing layer is meant to be a first, coarse filter (no slash in `:filename` for most model types means a classic `../etc/passwd`-shaped payload can't even match the route and 404s before the controller runs at all); the controller-level `check_path_traversal!` is the second, fine-grained filter. For the `appearance` model specifically, only the second filter is in place — the routing layer permits slashes and arbitrary content including `..`.

**Broken assumption:** that route-level filename constraints are a uniform, redundant defense-in-depth layer across all upload-serving routes. They are not — one route family (chosen, plausibly, because instance logos/favicons might legitimately need a `.` in a versioned filename, or simply an oversight) is a single-layer-of-defense outlier among six otherwise-consistent route definitions in the same file.

**Expected behavior:** `filename: %r{[^/]+}` (or an equally strict pattern) on every route dispatching to the same traversal-sensitive controller action.

**Actual behavior:** `filename: /.+/` on the appearance route only, confirmed by direct read of the current routes file.

**Required preconditions:** none beyond the route being reachable (it is, by design, unauthenticated). The only remaining defense for this specific route is the controller-level `check_path_traversal!` call — meaning this finding's real-world exploitability is entirely contingent on that single remaining check being correct and always executed, which is exactly the single point of failure this document's Finding 3 and [PATCH_ARCHAEOLOGY.md Entry 2](PATCH_ARCHAEOLOGY.md) already show has had architecturally-similar gaps elsewhere (the Rack middleware's exemptions) in this same codebase's history.

**Potential impact:** low **on its own** (the controller check still runs and, per this pass's reading, appears correctly implemented with no gating feature flag on this specific call, unlike the Rack middleware); the impact would only materialize if `check_path_traversal!`'s regex has any bypassable edge case (double-encoding, an unusual separator, a normalization difference between `CGI.unescape`/`Gitlab::Utils.decode_path` and whatever the underlying `File`/CarrierWave storage layer does with the string) — none of which were confirmed as an actual bypass in this pass, only flagged as open questions in [SECURITY_INVARIANTS.md INV-02](SECURITY_INVARIANTS.md).

**Confidence:** Medium on the routing inconsistency being real and exactly as described (directly read); Low on it being independently exploitable, since it reduces to "is the one remaining check actually sound," which was not confirmed broken.

**Exact source locations:** `config/routes/uploads.rb:4-11` vs `:24-27` (the exact `filename` constraint diff); `app/controllers/concerns/uploads_actions.rb:49-50`.

**Why the issue is exploitable (conditionally):** because this route removes one of the two independent layers of defense that every sibling route has, an attacker attacking this specific route only needs to defeat `Gitlab::PathTraversal.check_path_traversal!`'s regex once — with no route-level pre-filter acting as a second obstacle — making this the single lowest-defense-in-depth entry point in the entire upload-serving route table, even though no concrete bypass of the remaining check was found.

## Framework questions addressed but resulting in no finding (recorded for completeness, per instruction not to report only positive results without showing the work)

- **Q3 (can attacker-controlled data change after validation, TOCTOU):** `uploads#show`'s `uploader` lookup (`build_uploader_from_upload`) requires an exact-match `Upload.find_by(model:, uploader:, path:)` DB row to exist; `check_path_traversal!` runs before that lookup and the lookup itself is a single atomic query — no TOCTOU window identified in this specific flow.
- **Q6 (identity/context confusion):** `FileUploader#secret` is validated by `VALID_SECRET_PATTERN` (10-32 hex chars) at first use via CarrierWave's own path-building methods (`dynamic_segment`), independent of whether the traversal check on `filename_param` runs — `secret_param` cannot itself carry a traversal payload because any non-matching value raises `InvalidSecret`, which `UploadsActions` explicitly rescues to a 404. No finding.
- **Q8 (alternate HTTP methods):** every upload route in `config/routes/uploads.rb` is verb-pinned (`get`/`post`, no bare `match`); no finding.
- **Q9 (alternate content types reaching the same parser):** `set_request_format_from_path_extension` remaps `.js` to `:text` specifically to avoid Rails' cross-origin JS format handling — this is a deliberate, narrow mitigation for a specific historical concern (browser same-origin script inclusion), not an open gap found in this pass; a full audit of every other format this method could resolve to was not completed and is a candidate for a follow-up pass, not a finding here.

## What was not done

- The `PendingDirectUpload` class body (referenced by, but not defined in, `app/uploaders/object_storage.rb`) was not located in this sparse checkout and its exact-match/ownership semantics remain unconfirmed (Finding 1's central open question).
- A full enumeration of every Grape endpoint declaring a `file.remote_id`/`file.path` parameter (beyond `lib/api/project_import.rb`, found by targeted grep) was not completed.
- No attempt was made to determine, for any real deployment, whether Rails/Puma is ever reachable without passing through gitlab-workhorse first (Finding 2's central open question) — this is inherently a live-instance/network question, not a source-reading one.
- Q11 (state-transition ordering), Q12 (races), Q13 (low-priv → high-priv), Q14 (cross-tenant identifiers), Q15 (internal endpoint reached externally) were considered but did not surface a concrete, citable call chain distinct from Findings 1–4 above within this pass's time budget, and are not force-fitted into findings here.

No exploitation has been attempted against any instance. Waiting for instruction before any live validation begins.
