# THREAT_MODEL.md — GitLab (self-managed instance)

Scope authority: [TARGET_SELECTION.md](TARGET_SELECTION.md) — testing only against my own GitLab instance, never gitlab.com. This document derives its priorities from two prior artifacts: [SYSTEM_CONTEXT.md](SYSTEM_CONTEXT.md) (architecture, as read from current source) and [HISTORICAL_VULNERABILITY_MODEL.md](HISTORICAL_VULNERABILITY_MODEL.md) (24 disclosed vulnerabilities across 14 classes, each cited). No new research claims are introduced here; every prioritization decision below points back to a specific numbered entry in those two documents. No testing has been performed — this is a prioritization document only.

## How priority was assigned

A candidate research area scores higher when it has **all three** of:
1. **Historical density** — multiple disclosed CVEs/reports in the same class (recurrence), not a single one-off.
2. **Architectural persistence** — the code/architecture that caused the historical bug is confirmed, by direct source reading, to still exist in essentially the same shape today (cited to the specific [SYSTEM_CONTEXT.md](SYSTEM_CONTEXT.md) section).
3. **Bounty alignment** — the class is not excluded or de-prioritized by [TARGET_SELECTION.md](TARGET_SELECTION.md)'s program policy (e.g., DoS-only findings, pure enumeration, and prompt-injection-only findings are down-weighted regardless of historical density, because the program will not reward them).

## Tier 1 — Highest priority (recur, architecture confirmed unchanged, bounty-eligible at Critical/High)

### T1-A. Path traversal in file/repository-serving routes
- **Evidence:** [HISTORICAL_VULNERABILITY_MODEL.md Class 2](HISTORICAL_VULNERABILITY_MODEL.md) — CVE-2023-2825 (2023, unauthenticated arbitrary file read via nested-group upload path, CVSS 10.0) and the **currently active** CVE-2026-85706 (repository-commits API path traversal, CVSS 10.0, CISA KEV) cited in [TARGET_SELECTION.md](TARGET_SELECTION.md). Same class, same severity, three years apart, still happening as of the most recent patch release available.
- **Architecture link:** [SYSTEM_CONTEXT.md §6](SYSTEM_CONTEXT.md) documents the *current* defense for this class (`UploadedFile.from_params` → `File.realpath` + fixed allowlist) as "the single highest-value invariant in the file-upload flow" — but that defense covers the **upload/Workhorse-JWT** path specifically. CVE-2023-2825 and CVE-2026-85706 both hit **file-serving/API routes that build a path from a request parameter directly**, a different code path than the hardened upload allowlist. This is exactly the kind of "the fix covers one path but not the structurally similar one next to it" gap this codebase has repeatedly shown (see also T1-B).
- **Why Tier 1, not just "recently patched so done":** the pattern (group/namespace-nesting-dependent path construction, or ID+filename-based route construction, with insufficient canonicalization) is a *repeatable construction mistake*, not a single bug — any endpoint that builds a filesystem or repository path from a URL segment or API parameter without routing it through the `File.realpath`+allowlist pattern is a candidate.
- **Where to look first (own GDK/Docker instance only):** every controller/API route that accepts a project/group path *and* a secondary file/ref/path parameter and reads from disk or Gitaly using string concatenation rather than the vetted uploader/allowlist helpers — repository archive/blob/diff download endpoints, wiki attachment routes, design-management image routes, package-registry file routes (`lib/api/internal` list in [SYSTEM_CONTEXT.md §1](SYSTEM_CONTEXT.md)), and any endpoint added or changed since the 19.3.2 patch release.
- **Bounty alignment:** Critical, In-scope, no DoS/enumeration ambiguity — one of the cleanest bounty-eligible classes in the whole document.

### T1-B. Unsafe/open redirect → OAuth token / CSRF-token exfiltration
- **Evidence:** [HISTORICAL_VULNERABILITY_MODEL.md Class 3](HISTORICAL_VULNERABILITY_MODEL.md) — **five** distinct disclosed instances of the identical root cause (protocol-relative/absolute-URL confusion from a leading-slash or path-building bug) spanning **2017 → 2022 → 2022 (incomplete fix) → 2024 (×2)**. This is the single most-recurring architectural flaw found in this research: GitLab's own engineers documented, in a public issue ([GitLab #377810](https://gitlab.com/gitlab-org/gitlab/-/issues/377810)), that their own CVE-2022-2250 fix missed sibling routes with the same construction bug, and the same *shape* of bug (open redirect breaking the OAuth flow) reappeared in 2024 as two separate CVEs in one patch release.
- **Architecture link:** [SYSTEM_CONTEXT.md §14](SYSTEM_CONTEXT.md) flags GitLab as both an OAuth/OIDC client and provider with many separate strategy integrations and a device-code grant — a large surface of separate redirect-URI-handling code paths, which is exactly the shape that let this bug recur (many independent places build/validate "is this URL safe to redirect to," and historically not all of them agreed).
- **Why Tier 1:** five recurrences over seven years, in a program that pays $20k–$35k for Critical, on a code shape (path/redirect building) that is easy to audit by grep for `location.pathname`/path-concatenation patterns without a full understanding of the whole app.
- **Where to look first:** any redirect-target or "next path" parameter derived from a route segment rather than a validated allowlist, particularly around OmniAuth callback URLs, Jira Connect (site of the original CVE-2022-2250), and any newer OAuth-adjacent flow (Doorkeeper device-authorization grant is newer code, per [SYSTEM_CONTEXT.md §14](SYSTEM_CONTEXT.md), and hasn't had the multi-year hardening the older Jira DVCS path has had).
- **Bounty alignment:** High severity historically (CVSS 6.1–8.x range); open redirect *alone* is explicitly a lower-priority/borderline class per general bounty norms, but **chained to OAuth-token exfiltration or account takeover** (as every historical instance here was) it is squarely High/Critical and bounty-eligible — the research question is specifically "does this redirect chain reach a token-bearing flow," not "does an open redirect exist."

### T1-C. CI/CD pipeline identity/authorization confusion
- **Evidence:** [HISTORICAL_VULNERABILITY_MODEL.md Class 11](HISTORICAL_VULNERABILITY_MODEL.md) — CVE-2024-6385 and CVE-2024-5655 (both CVSS 9.6, both "run a pipeline as an arbitrary user," 2 weeks apart), CVE-2024-9164 (arbitrary branch pipeline execution), CVE-2024-8641 (job-token-to-session-token escalation), CVE-2024-11669 (job-token scope applied too broadly) — **five** distinct CVEs, all in CI/CD identity/authorization, all in a single year.
- **Architecture link:** [SYSTEM_CONTEXT.md §2](SYSTEM_CONTEXT.md) documents the CI job token as one of ~10 parallel credential types handled by the same `AuthFinders` chain, and separately flags ([SYSTEM_CONTEXT.md §4](SYSTEM_CONTEXT.md)) that Sidekiq-executed, CI-triggered work can suffer from "the authorization decision made at enqueue time may be stale by execution time" — precisely the invariant that failed in CVE-2024-11222 ([Class 14.2](HISTORICAL_VULNERABILITY_MODEL.md)) and is architecturally the same shape as the undisclosed mechanism in CVE-2024-6385/-5655.
- **Why Tier 1:** highest CVE density of any single class in the historical record (5 CVEs in ~5 months), directly tied to a credential/identity model that [SYSTEM_CONTEXT.md](SYSTEM_CONTEXT.md) independently flagged as complex (10 parallel credential types) before this document's research began — convergent evidence from two independent methods (source reading and CVE mining).
- **Where to look first:** the boundary between "which user identity does a triggered/scheduled/retried pipeline execute as," job-token-scope enforcement completeness across *all* API endpoints (not just the obvious ones — this was the exact gap in CVE-2024-11669), and any code path where a job token can be exchanged for or used to derive a different credential type (the CVE-2024-8641 shape).
- **Bounty alignment:** Critical (CVSS 9.6 class), clean "business-logic authorization" — GitLab's own program guidance treats this class as core, non-excluded scope.

## Tier 2 — High priority (recur or high-impact, architecture partially confirmed, some caveats)

### T2-A. IDOR/BOLA via ID-keyed API lookups skipping visibility/confidentiality checks
- **Evidence:** [Class 12](HISTORICAL_VULNERABILITY_MODEL.md) — 4 CVEs, 2022 through 2026 (CVE-2022-1352, -1545, CVE-2026-1080, CVE-2025-14594), all the same shape: an endpoint that accepts a numeric ID/IID and returns data without re-checking the containing project/group's visibility or confidentiality setting.
- **Architecture link:** [SYSTEM_CONTEXT.md §3 and Flow C](SYSTEM_CONTEXT.md) independently identified, from reading the DeclarativePolicy/GraphQL-authorization code, that **REST and GraphQL maintain separate authorization declarations over the same underlying models**, and explicitly named "a resolver that queries the model directly instead of via the Finder" as the highest-suspicion pattern — this is the same mechanism that produced 12.1/CVE-2026-1080 (iterations API reaching private descendant-group data) and CVE-2025-14594 (pipeline-data IDOR).
- **Why Tier 2 not Tier 1:** individual instances tend to be Medium severity (CVSS ~5.3 for the oldest one) rather than Critical, though the two most recent instances (2025/2026) suggest the pattern is still live and worth checking against newer API surface (Organizations, iterations, newer GraphQL types) which is comparatively less battle-tested per [SYSTEM_CONTEXT.md §4](SYSTEM_CONTEXT.md).
- **Where to look first:** any GraphQL resolver or REST Grape endpoint that takes a bare ID/IID/GlobalID and fetches a record directly (`Model.find`) rather than through a project-scoped Finder; compare the same underlying object's exposure across its REST and GraphQL surfaces for behavioral differences (confidential issues/notes, iterations, work items, pipeline data are the four areas with prior confirmed history).
- **Bounty alignment:** Medium–High typically; still bounty-eligible and the exact "privacy breach exposing confidential data" carve-in the program explicitly rewards ([TARGET_SELECTION.md](TARGET_SELECTION.md) "In scope examples").

### T2-B. Deserialization / attacker-authored structured input (import-export, GraphQL subscriptions)
- **Evidence:** CVE-2026-87719 (GraphQL subscription-serializer insecure deserialization, Critical CVSS 9.9, cited in [TARGET_SELECTION.md](TARGET_SELECTION.md)/[HISTORICAL_VULNERABILITY_MODEL.md Class 15](HISTORICAL_VULNERABILITY_MODEL.md)) is the only fully-identified GitLab-specific deserialization CVE found in this pass; CVE-2022-2884 ([Class 5](HISTORICAL_VULNERABILITY_MODEL.md)) is adjacent (attacker-controlled import data reaching a dangerous sink, though a command-injection sink rather than a deserialization one).
- **Architecture link:** [SYSTEM_CONTEXT.md §10/11](SYSTEM_CONTEXT.md) independently flagged Import/Export as "the standout risk area" for exactly this reason — an attacker-authored, complex structured file (project/group export tarball) that gets parsed and partially trusted — and *positively confirmed* (by reading `lib/gitlab/import_export/config.rb` and `attributes_permitter.rb`) that GitLab already uses `YAML.safe_load_file` with a `permitted_classes` allowlist and an explicit attribute-permitter, i.e. the obvious top-level deserialization bug is already mitigated.
- **Why Tier 2 not Tier 1:** the "easy" version of this bug class (unsafe YAML/Marshal load) is confirmed absent from the main import/export path; the real risk is in *less obvious* deserialization-adjacent surfaces — the GraphQL subscription serializer (per the live CVE-2026-87719) and any Sidekiq-argument or cache-layer serialization that doesn't go through the same hardened path. This requires deeper, more speculative source review than T1 items before a concrete lead exists.
- **Where to look first:** GraphQL subscription payload construction/serialization (the exact area of CVE-2026-87719 — check whether the specific 2026-09 fix was complete or, per the recurring pattern in this document, addressed only the reported PoC); any custom `Marshal`/`Psych`/`Oj` usage outside the already-audited import/export path, especially anywhere Sidekiq job arguments or cache values are round-tripped through a non-JSON serializer.
- **Bounty alignment:** Critical when it lands; the research cost to find a *new* instance is higher than T1 items since the obvious path is already hardened.

### T2-C. Memory corruption in native/C-extension gem dependencies reachable from attacker content
- **Evidence:** [Class 7](HISTORICAL_VULNERABILITY_MODEL.md) — the Oj-gem RCE chain (CVE-2026-54902 + 8 sibling CVEs), fully mechanism-documented by an independent researcher, as recent as mid-2026.
- **Architecture link:** [SYSTEM_CONTEXT.md §15](SYSTEM_CONTEXT.md) flagged native/non-Ruby components as a lower-likelihood-but-real risk area; this historical finding is a concrete confirmation that a **pure-Ruby web app can still ship memory-corruption RCE** via a native-extension dependency (Oj) fed with ordinary, low-privilege, attacker-supplied repository content (a `.ipynb` file).
- **Why Tier 2 not Tier 1:** exploiting this class requires genuine low-level skills (ASLR defeat via heap-pointer leak, multi-stage heap-grooming) far beyond source review, and the *specific* Oj bug is already fixed; the actionable research angle is narrower — auditing **other** call sites of Oj (or other native JSON/YAML/XML gems: `nokogiri`, `rexml`, `oj-introspect`) that accept raw, low-privilege-attacker-controlled bytes (not just `.ipynb` diffing), since the researcher's writeup explicitly notes Oj is GitLab's general-purpose JSON gem, not notebook-specific.
- **Where to look first:** grep for every call site of `Oj::Parser`/`Oj.load` reachable from user-supplied repository content, issue/MR bodies, or import data, and check whether GitLab is current on the Oj (and Nokogiri, given Nokogiri's own CVE history) version relative to the fixed releases identified in [Class 7](HISTORICAL_VULNERABILITY_MODEL.md).
- **Bounty alignment:** Critical when found — but also flagged in [Class 7 point 11](HISTORICAL_VULNERABILITY_MODEL.md) as a case GitLab did not even file as a security advisory, which is a signal that dependency-version-lag bugs in this specific gem may be under-triaged and worth re-checking against the *current* Gemfile.lock rather than assuming the whole class is closed.

### T2-D. SAML/SSO authentication-bypass surface (parser differentials, library-version lag)
- **Evidence:** [Class 8](HISTORICAL_VULNERABILITY_MODEL.md) — CVE-2024-45409 (Critical, CVSS 10.0, full auth bypass), with a specifically-noted follow-on `ruby-saml` CVE (CVE-2025-25292) in GitLab's own advisory database.
- **Architecture link:** [SYSTEM_CONTEXT.md §2](SYSTEM_CONTEXT.md) confirmed, by reading the current `Gemfile`, that GitLab still depends on the same `ruby-saml`/`rexml`/`omniauth-saml` combination that produced this bug, and separately flagged `ruby-saml`/`rexml`'s upstream history of parser-differential-class bugs as "worth diffing against the CVE history of those gems specifically" — written *before* this historical research confirmed exactly that history exists.
- **Why Tier 2, not Tier 1:** this is a **dependency-currency** check, not a from-scratch research task — the highest-value action is verifying the exact installed `ruby-saml`/`rexml` version against the fixed-version list, which is fast and conclusive, but it is not "new" research once done (either the instance is current and this line closes, or it's behind and the historical exploit applies almost verbatim).
- **Where to look first:** `Gemfile.lock` version pin for `ruby-saml`, `rexml`, `omniauth-saml`, `nokogiri` on the actual test instance; if current, this line is closed rather than actively researched further.
- **Bounty alignment:** only relevant on SSO-enabled test instances (self-managed, so directly achievable in a GDK/Docker lab); Critical if found.

## Tier 3 — Worth checking, lower expected yield or harder to convert into a bounty-eligible finding

### T3-A. SSRF via webhooks/imports (DNS rebinding class)
- **Evidence:** [Class 1](HISTORICAL_VULNERABILITY_MODEL.md), the highest-*volume* historical class (3+ independent reports in 2019 alone).
- **Why Tier 3, not Tier 1, despite the volume:** [SYSTEM_CONTEXT.md §13](SYSTEM_CONTEXT.md) already did the deep source read for this exact class and found the *specific* 2019 bug's fix (`dns_rebind_protection`/`enforce_uri_hostname` IP-pinning) is now correctly implemented and active at request time in `Gitlab::HTTP`. The remaining risk — flagged explicitly in that section — is narrow and specific: **a new code path that sends an outbound request using a stored/attacker-influenced URL without going through `Gitlab::HTTP`** (e.g., a gem doing its own resolution, or a raw `Net::HTTP` call). This is a real, worthwhile check, but it is a *hunt for a new bypass of an already-hardened control*, not a wide-open recurring gap — hence Tier 3 (specific, plausible, but narrower than the Tier 1 items where the historical *fix itself* has a documented gap).
- **Where to look first:** every integration that fetches a user-configured URL (avatar-by-URL, remote mirrors, dependency proxy, CI/CD component sources, "import project by URL", any newer AI/Duo integration that fetches external content) — specifically checking which HTTP client library each one uses.
- **Bounty alignment:** Critical/High if a genuine bypass of the *current* mitigation is found; but the base "webhook can SSRF" report is a well-known, heavily-tested area on this program (implied by the sheer number of historical duplicate reports), so novelty is the binding constraint, per [TARGET_SELECTION.md](TARGET_SELECTION.md)'s note on duplicate-heavy competition.

### T3-B. Race conditions around approval/pipeline gating
- **Evidence:** [Class 14](HISTORICAL_VULNERABILITY_MODEL.md) — 2 CVEs, five years apart, same TOCTOU shape.
- **Why Tier 3:** genuinely recurring, but each historical instance required non-trivial timing/concurrency engineering to exploit (not a simple parameter or path bug), and severity has been Low–Medium in both confirmed cases — lower expected payout per unit of research effort than the Tier 1 items, though not dismissible given it overlaps with the higher-value Tier 1-C (CI/CD identity) surface.
- **Where to look first:** any place a permission/gating check and the corresponding state-changing action are not wrapped in the same DB transaction/lock — a classic source-review target rather than a black-box one.

### T3-C. Workhorse request smuggling / route-matcher bypass
- **Evidence:** [Class 13](HISTORICAL_VULNERABILITY_MODEL.md) — 3 CVEs, one release (2020), not recurring since.
- **Why Tier 3:** [SYSTEM_CONTEXT.md §1](SYSTEM_CONTEXT.md) confirms the *architecture* (large regex+matcher route table in `routes.go`) that caused this is still in place, so the class is architecturally possible, but there is no evidence of a repeat in 6 years, suggesting the original bypass techniques were durably closed and a new one would require genuine protocol-level (HTTP smuggling) expertise rather than source reading alone.
- **Where to look first:** any *recently added* route in `routes.go` with a matcher that is weaker or differently-scoped than its neighbors (the newer AI/Duo-workflow and observability routes are the least battle-tested, per their 2024+ addition dates visible in the source).

### T3-D. Business-logic authorization bugs in newer, less-battle-tested surfaces (Organizations, Duo/Agent Platform, CI/CD Components)
- **Evidence:** no direct historical CVE found for these *specific* newer features (stated as a gap, not invented) — this entry is included because [SYSTEM_CONTEXT.md §4/§5](SYSTEM_CONTEXT.md) independently flagged Organizations and the Agent Platform as newer, comparatively less-hardened constructs, and the *general pattern* underlying nearly every Tier 1/2 class above ("a security control exists but wasn't applied to every equivalent code path/newer feature") strongly predicts these newer surfaces are where the *next* instance of an already-recurring class will appear.
- **Why Tier 3, not higher:** speculative by construction — there is no historical CVE to anchor it to, only an architectural inference from other classes' recurrence pattern. Included for completeness because the prompt asked the threat model to reflect where evidence *points*, and repeatedly, evidence here points to "new feature area + old recurring pattern" as the predictive combination.
- **Bounty alignment caveat:** prompt-injection findings against the Agent Platform specifically are **excluded** by the program policy except where they cross a security boundary ([TARGET_SELECTION.md](TARGET_SELECTION.md) "AI related vulnerabilities" / the listed known-issue table) — so research here must target conventional authorization logic around the agent/tool boundary, not prompt-injection content itself.

## Explicitly de-prioritized (bounty policy conflict, regardless of historical interest)

- **DoS of any kind**, including the historically-real GraphQL-complexity-limiter DoS CVEs seen in [TARGET_SELECTION.md](TARGET_SELECTION.md)'s patch-release table (CVE-2025-14871, CVE-2026-1168) — the program excludes DoS except a narrow unauthenticated-persistent-total-disruption carve-out, and volumetric/rate-limiting findings are explicitly ineligible.
- **Enumeration/metadata-disclosure-only findings** (project/user existence, timing oracles) — explicitly out of scope per policy, even though this class has historical CVE presence in the broader industry; not worth researching here regardless of technical interest.
- **CSRF as a bare finding** — Class 4 shows CSRF does still occur (CVE-2026-19650, 2026), so it's not dismissed as a class, but a CSRF report without a concrete state-changing action reachable through it is unlikely to score above Low; treat as a secondary finding to chain onto something else (as the 2017 CSRF-token-leak report explicitly did, feeding into account-level impact) rather than a primary target.
- **Prompt injection (standalone)** — explicitly excluded by policy; the historical record in this document also does not contain a single disclosed *prompt-injection* CVE (the closest AI-adjacent item, CVE-2026-87719, is a conventional deserialization bug in AI-feature-adjacent GraphQL code, not a prompt-injection bug), so there is no historical pull toward this class either.

## Net recommendation

Given evidence density, confirmed-current architecture, and bounty alignment, the highest-expected-value next step is **Tier 1-A (path traversal in file/repository-serving routes)**: it has the cleanest two-CVE recurrence with matching severity three years apart, a clearly identified "hardened path exists here, but not there" architectural gap already documented in [SYSTEM_CONTEXT.md §6](SYSTEM_CONTEXT.md), and zero ambiguity about bounty eligibility (Critical, explicitly in-scope, not enumeration/DoS-adjacent). **Tier 1-C (CI/CD pipeline identity)** is the second-highest-value target given its unmatched CVE density (5 in one class-year) and direct overlap with the credential-model complexity independently flagged in [SYSTEM_CONTEXT.md §2](SYSTEM_CONTEXT.md), though GitLab's non-disclosure of the exact CVE-2024-6385/-5655 mechanism means this line requires more from-scratch source analysis before a concrete lead exists.

## Living invariant tracker (added after [AUTHZ_AUDIT.md](AUTHZ_AUDIT.md) and [PATCH_BYPASS_MATRIX.md](PATCH_BYPASS_MATRIX.md); updated as research continues, not a static snapshot)

### A. CONFIRMED SECURITY INVARIANTS (read directly from current source, verified sound)
- GraphQL type-level `authorize` correctly gates every bare-`object_from_id` resolver traced in [AUTHZ_AUDIT.md Area 1](AUTHZ_AUDIT.md), including finer-grained per-field gates (e.g. `read_runner` vs. `read_runner_sensitive_data` on `Ci::RunnerType`).
- The ancestor/descendant-group-expansion re-scoping fix for the CVE-2026-1080 bug class generalized correctly to its nearest sibling (`IterationsFinder` and `Iterations::CadencesFinder` both re-check per-group access, [AUTHZ_AUDIT.md Area 2](AUTHZ_AUDIT.md)).
- **New this session:** every "authorize source, act on destination" move/transfer operation checked (`Issues::Move`, `WorkItems::BulkMove`, `Projects::Transfer`, `Groups::Transfer`) independently authorizes *both* the source and destination object, via a shared service-layer check one level below the mutation ([PATCH_BYPASS_MATRIX.md](PATCH_BYPASS_MATRIX.md)) — this is now an established, confirmed convention in this codebase, not a one-off.
- `Types::UserType` has no `email`/`public_email` field at all — the CVE-2022-1352-class "sibling API leaks a sensitive field" risk doesn't apply to it because there's nothing there to leak.

### B. SUSPECTED SECURITY INVARIANTS (plausible, not yet proven or disproven — the active research queue)

### D. Updated Tier-1 priority note
The Tier 1-B (open-redirect/OAuth chain) entry above should be read together with this resolution: the *specific* two named sibling routes are no longer this class's best lead (one is fixed, the other has a real but middleware-gated gap requiring one narrow live check). The single highest-value next action across this entire engagement is now the one-request test described in [PATCH_BYPASS_MATRIX.md](PATCH_BYPASS_MATRIX.md)'s sibling-B section — the fastest path in this whole research chain from "source-level candidate" to "CONFIRMED or FALSE POSITIVE," if a self-owned test instance becomes available.

**Live validation attempted, blocked, then resolved anyway (across two sessions):** the specified single request was never sent (`docker`/`ruby` not installed, no local instance listening — NOT TESTABLE). But the actual open question wasn't "send a request," it was "what is the middleware's default state" — a static fact already sitting in the source tree. `config/feature_flags/ops/check_path_traversal_middleware.yml` reads `default_enabled: true`, milestone 16.5. **Result: MITIGATED BY DEFAULT**, resolved without any live instance. The lesson worth keeping: before queuing something as "requires live validation," check whether the source tree itself (a feature-flag YAML, a `Gemfile.lock` pin, a config default) already answers it — two of this engagement's three open live-dependent questions turned out to be answerable this way.
