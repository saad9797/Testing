## CVE-2022-2250 sibling-route resolution (this session, focused follow-up on the previously-open lead)

**Historical vulnerability:** CVE-2022-2250 — open redirect via an unsanitized decoded path segment, root cause in `lib/gitlab/jira/dvcs.rb#restore_full_path`, exploited to exfiltrate OAuth-provider access tokens by chaining redirects. GitLab's own follow-up issue [#377810](https://gitlab.com/gitlab-org/gitlab/-/issues/377810) stated the original fix (`gsub(%r{\/{2,}}, '/')` alone) was incomplete and named two sibling routes that reproduced the underlying problem through a different call path.

**Precise invariant violated (restated after reading the exact original PoC text this session, not just a paraphrase):** two distinct but related invariants, one per sibling —
- *Sibling A (`commit/:id`, `tree/*id`)*: the exact invariant from CVE-2022-2250 itself — a project-path string built from a decoded, attacker-influenced segment can't itself start with `/` or contain `//`, because both routes build their final redirect target as `"/#{project_full_path}/..."`, and a `project_full_path` that already starts with `/` produces a leading `//` (protocol-relative URL).
- *Sibling B (`logs_tree/*path`)*: a **related but mechanically different** invariant — the original PoC (`.../logs_tree/../../../../../`) is a **path-traversal-based** redirect-target manipulation, not a leading-slash/protocol-relative one. The wildcard `*path` segment is interpolated into a redirect-target template with no traversal check at all, letting an attacker walk the resulting same-origin redirect target to an arbitrary other same-origin path — the actual exploit chain requires that other path to itself be (or lead to) a cross-origin redirect, hence issue #377810's title "chaining **multiple** redirects."

**Sibling A — traced fully, current source:**
```
config/routes/project.rb:733-740 (commit/:id) and :742-749 (tree/*id)
  both: project_full_path = ::Gitlab::Jira::Dvcs.restore_full_path(namespace: params[:namespace_id], project: params[:project_id])
        "/#{project_full_path}/commit/#{params[:id]}"   # (or /-/tree/... for the second route)

lib/gitlab/jira/dvcs.rb:39-47  restore_full_path  (CURRENT source, re-read this session)
  if project.include?(ENCODED_SLASH)
    project.gsub(ENCODED_SLASH, SLASH).gsub(%r{\/{2,}}, '/').gsub(%r{^\/}, '')
                                        ^^^^^^^^^^^^^^^^^^^^  ^^^^^^^^^^^^^^^^
                                        (present in the 2022 fix)   (NEW — not present in the
                                                                      original fixing commit
                                                                      178947a1 diffed in
                                                                      PATCH_ARCHAEOLOGY.md Entry 1)
  else
    "#{namespace}/#{project}"   # namespace/project constrained to Gitlab::Jira::Dvcs::ENCODED_ROUTE_REGEX,
                                 # which excludes '/' entirely — this branch can't produce a leading slash either
```
The function now has a **third gsub, added at some point after the original 2022 fix**, that strips any leading `/` from its output. Combined with the second gsub (which guarantees no `//` survives anywhere in the string), `restore_full_path`'s return value can never start with `/` and never contains `//` — so `"/#{project_full_path}/commit/#{id}"` is structurally guaranteed to have exactly one leading slash and no embedded `//`, i.e. it can never be interpreted as protocol-relative. Both named sibling routes call this same, now-more-thoroughly-hardened function.

**Verdict: DISPROVEN.** Both routes named in #377810 for the CVE-2022-2250 mechanism specifically are no longer vulnerable to it — not because the routes themselves changed, but because the shared function they both call was hardened further (a third gsub) at some point after the incomplete-fix issue was filed. This is a genuine, source-confirmed resolution of a previously-open lead.

**Sibling B — traced fully, current source:**
```
config/routes/repository_deprecated.rb:20-26  (CURRENT source, re-read this session)
  get '/refs/:id/logs_tree/*path',
      constraints: { id: /.*/, path: /[^\0]*/ },   # <-- still accepts ANY character except null, including '../'
      to: redirect { |params, _request|
        path = params[:path]
        path.gsub!('@', '-/')                       # only substitutes '@' -> '-/'; NOT a traversal/canonicalization guard
        Addressable::URI.escape("#{params[:namespace_id]}/#{params[:project_id]}/-/refs/#{params[:id]}/logs_tree/#{path}")
      }                                              # Addressable::URI.escape percent-encodes unsafe chars; '.' and '/'
                                                       # are valid URI path characters and pass through unescaped
```
Compared against the **original vulnerable version** (quoted verbatim from issue #377810 this session): `to: redirect('%{namespace_id}/%{project_id}/-/refs/%{id}/logs_tree/%{path}')`. The route changed from Rails' string-pattern `redirect(...)` to a Proc-based `redirect { ... }`, and gained the `@`→`-/` substitution and an `Addressable::URI.escape` wrapper — **neither of which is a path-traversal check**. `Gitlab::PathTraversal.check_path_traversal!`/`path_traversal?` is not called anywhere in this route or its handler. The exact `../../../../../` payload from the original public PoC would still be interpolated into the redirect target unchanged by this route's own code today.

**Verdict: CONFIRMED SOURCE-LEVEL VULNERABILITY** at the route level — this specific sibling was not hardened the way sibling A was (it never called the `Dvcs.restore_full_path` function to begin with, so that fix couldn't have reached it either way).

**Delegation check (per the instruction not to conclude "vulnerable" from an in-file absence alone):** [SLICE_01_DEEP_FINDINGS.md](SLICE_01_DEEP_FINDINGS.md)/[SLICE_01_FINDINGS.md Finding 3](SLICE_01_FINDINGS.md) already established that GitLab has a **separate, general-purpose, feature-flagged Rack middleware** (`lib/gitlab/middleware/path_traversal_check.rb`) that inspects `request.fullpath` for exactly the `[/\\]\.\.[/\\]`-shaped pattern this payload contains, and would run *before* Rails routing dispatches to this specific route's handler. A literal `../` in the raw URL path (not URL-encoded, not hidden in one of the 12 exempted query-parameter names — this is the URL *path* itself, not a query string) would match that middleware's check. **This means the route's own code is a confirmed gap, but whether it is practically reachable depends entirely on whether `Feature.enabled?(:check_path_traversal_middleware, ...)` is true on the target instance** — a flag whose current default/rollout state was not determined in this session (no live instance available to check `Feature.get(:check_path_traversal_middleware).state`, and the flag's default value is not hardcoded in the file itself, per [SLICE_01_FINDINGS.md](SLICE_01_FINDINGS.md)'s original reading).

**Overall classification for Sibling B, updated (see the "Resolved without a live instance" note below the table): MITIGATED BY DEFAULT.** `check_path_traversal_middleware` is `default_enabled: true` since GitLab 16.5 (`config/feature_flags/ops/check_path_traversal_middleware.yml`), read directly from the source tree — no live instance was needed to resolve the one remaining external fact this classification depended on. The route-level defect itself remains real and unfixed in this specific file's own code, but it is not exploitable on a standard, unmodified instance.

**Remaining uncertainty:**
1. The `check_path_traversal_middleware` feature flag's actual state on a representative current instance (GDK default, Omnibus default, and gitlab.com's actual production state may all differ).
2. Whether Rails' own route-matching for a `*path` glob segment could itself normalize/reject a raw `../`-containing URL before the middleware or the redirect block ever sees it (plausible but not verified against this specific Rails version's `ActionDispatch::Journey` behavior).
3. Whether, if the middleware is disabled or bypassed, the resulting same-origin redirect chain can actually be completed to a genuine cross-origin hop today — i.e., whether a second, currently-open redirect gadget still exists elsewhere in the app to complete the chain (not searched for in this session).

**Is a live instance now required?** Yes, specifically to answer question 1 above (a single read of `Feature.get(:check_path_traversal_middleware).state`, or a single crafted request to a self-hosted test instance) — this is a fast, narrow, conclusive check, not a broad live-testing campaign.

**Single highest-value next action:** on a self-owned test instance, either (a) check the feature flag's actual state directly, or (b) send exactly one synthetic request — `GET /<own-namespace>/<own-project>/refs/<any-ref>/logs_tree/../../../../<harmless-known-path>` — using only a self-created project, and observe whether the response is a 400 (middleware caught it) or a 3xx redirect containing the traversed, unsanitized path (middleware absent/disabled, confirming live exploitability of the route-level gap). No further escalation beyond this single observation is needed to resolve Sibling B's classification.

No live testing was performed to produce the above — it is entirely source-level, per this session's constraints (no running instance available, per [SCOPE_MATRIX.md](SCOPE_MATRIX.md)).

**Live validation attempt (prior session):** before sending the single specified request, preconditions were checked directly: `docker --version` → not found; `ruby -v` → not found; local ports 3000/8080 → connection refused/timeout. No self-owned or otherwise-authorized live instance exists in this environment. Per the explicit stop condition governing that validation step, **no request was sent**. Classification at that time: **NOT TESTABLE**.

**Resolved without a live instance (this session):** the remaining uncertainty was never actually "send a request" — it was "what is `check_path_traversal_middleware`'s state." That's a static fact recorded in the source tree itself, at `config/feature_flags/ops/check_path_traversal_middleware.yml`, which was pulled and read directly:
```yaml
default_enabled: true
milestone: '16.5'
introduced_by_url: https://gitlab.com/gitlab-org/gitlab/-/merge_requests/123477
```
The middleware has been **on by default since GitLab 16.5**. **Revised classification: MITIGATED BY DEFAULT.** On any standard, unmodified release-build instance from 16.5 onward, the middleware intercepts the literal `../` payload (`request.fullpath` containing `[/\\]\.\.[/\\]`, per [SLICE_01_FINDINGS.md Finding 3](SLICE_01_FINDINGS.md)) before `logs_tree/*path`'s handler ever executes, closing off the practical exploit path this session traced. The route's own code is still a genuine, uncleaned defect (it has no traversal check of its own, unlike its fixed sibling), but it is not currently a live vulnerability on a default configuration — only on an instance where an administrator has explicitly disabled this specific `ops`-type flag, which is not a normal or expected admin action. **No HackerOne submission is justified for this candidate.** This closes the single highest-priority open item from the previous session without requiring any live instance.

## New sibling-hunt detail (target-side authorization on move/transfer operations)

Traced this session, in full, as a direct instantiation of this document's own worked example ("Authorization check occurs before object lookup but object identity can be changed later" / "every sensitive object access must be authorized against the final resolved object"):

1. `Mutations::Issues::Move` (`app/graphql/mutations/issues/move.rb:22-44`) resolves `target_project` via `resolve_project(full_path: target_project_path)` with **no visible check in the mutation itself**, passing it straight to `WorkItems::DataSync::MoveService`. Traced one level deeper: `MoveService#verify_can_move_work_item` (`app/services/work_items/data_sync/move_service.rb:81-108`) calls `work_item.can_move?(current_user, target_namespace)`, which resolves to `Issue#can_move?` (`app/models/issue.rb:717-723`, since `WorkItem < Issue`): `return false unless user.can?(:admin_issue, to_namespace)`. **Target-side check present, just delegated into the model layer.**
2. `Mutations::WorkItems::BulkMove` → `WorkItems::BulkMoveService#execute` (`app/services/work_items/bulk_move_service.rb`) checks `@current_user.can?(:create_work_item, @target_namespace)` once for the batch (a coarse, lower-bar pre-check), then per-item calls the **same** `WorkItems::DataSync::MoveService.new(...).execute` as the single-move path — meaning the same `Issue#can_move?` target check applies per item regardless of the coarser batch pre-check. **Target-side check present and per-item, via the shared service.**
3. `Mutations::Projects::Transfer` (`app/graphql/mutations/projects/transfer.rb:29-46`) resolves `namespace` (the target) with no visible check in the mutation, passing it to `Projects::TransferService#schedule_async_transfer` → `ensure_allowed_transfer` (`app/services/projects/transfer_service.rb:146-162`): explicitly checks **both** `allowed_transfer_project?(current_user, project)` (`:change_namespace` on the source) **and** `allowed_to_transfer_to_namespace?(current_user, namespace)` (`:transfer_projects` on the target). **Both sides checked explicitly in the service.**
4. `Mutations::Groups::Transfer` → `Groups::TransferService` (`app/services/groups/transfer_service.rb:284-289`): explicitly checks `can?(current_user, :change_group, @group)` (source) **and** `can?(current_user, :create_subgroup, @new_parent_group)` / `can?(current_user, :create_group)` (target). **Both sides checked explicitly.**

**Conclusion:** the specific hypothesis "GitLab's move/transfer mutations authorize the source object in the resolver but forget the destination" — a direct, targeted test of this whole document's central worked example — is **disproven** for all four load-bearing mutations checked. The consistent shape across all four (mutation-level code authorizes only the source; the *service* layer, one level down, independently authorizes the destination) means this codebase's convention is to delegate destination-side authorization into services rather than omit it — worth recording as a now-established pattern for prioritizing *future* audit time toward mutations that do NOT follow this convention (i.e., where the destination is used directly by the mutation/resolver without a service-layer intermediary), rather than re-testing this specific, now four-times-confirmed-safe convention again.

No exploitation attempted. No live testing performed.
