Scope authority: [TARGET_SELECTION.md](TARGET_SELECTION.md). No testing performed. This document reads actual fixing diffs/commits (fetched from GitLab's own public commit/diff endpoints, GitHub Security Advisories for vendored gems, and disclosed HackerOne reports that quote vulnerable/fixed code verbatim) and cross-references them against the **current** source in the local checkout (`src/gitlab`, tag `v19.5.0-pre`) to find where the *fixed* code now lives and whether the same pattern recurs elsewhere. ## Entry 1 — Open redirect via undeduplicated `//` (CVE-2022-2250) and its acknowledged-incomplete fix

**Original vulnerable path:** `lib/gitlab/jira/dvcs.rb` — a decoded, attacker-influenced project-path string (`project.gsub(ENCODED_SLASH, SLASH)`) was used directly to build a redirect target for the Jira DVCS integration flow, with no check for embedded `//` sequences that a browser interprets as making the URL protocol-relative/absolute.

**Fixed path (commit `178947a12b763e54c87b93edde5fc596abd03ff3`, full diff read directly):**
```ruby
# before
project.gsub(ENCODED_SLASH, SLASH)
# after
project.gsub(ENCODED_SLASH, SLASH).gsub(%r{\/{2,}}, '/')
```
with an added comment ("Replace multiple slashes with single ones to make sure the redirect stays on the same host") and a new spec case titled `"malicious path"` testing that `/group/@@malicious.server` no longer redirects to `//malicious.server`.

**Security invariant:** a path/URL built from a decoded, attacker-influenced segment can never be interpreted as absolute/cross-origin by the browser or any downstream HTTP client (see [SECURITY_INVARIANTS.md INV-01](SECURITY_INVARIANTS.md)).

**Patch mechanism:** a **single regex substitution** (`gsub(%r{\/{2,}}, '/')`) collapsing consecutive slashes, applied at exactly one call site (`lib/gitlab/jira/dvcs.rb`).

**Residual assumptions the patch made (confirmed by GitLab's own follow-up):**
- That `lib/gitlab/jira/dvcs.rb` was the *only* place a decoded path segment reaches a redirect/URL-building step. GitLab's own public issue **[#377810](https://gitlab.com/gitlab-org/gitlab/-/issues/377810)** states explicitly this was false: `config/routes/project.rb` (`commit/:id`, `tree/*id`) and `config/routes/repository_deprecated.rb` (`/refs/:id/logs_tree/*path`) independently **prepend** a slash to a decoded path segment, producing the same protocol-relative-URL confusion through routes the Jira-specific fix never touched.
- That slash-deduplication (collapsing `//` → `/`) is sufficient in general. It only defeats the *specific* payload shape (repeated leading slashes); it does not canonicalize the path or validate the resulting host against an allowlist, so any other construction that yields a leading `//` *after* this substitution runs (e.g., a route that prepends its own separator *after* the dvcs.rb substitution has already executed) reproduces the bug through a different call order rather than a different payload.

**Sibling implementations (same "build a URL from a decoded path segment" shape):** the two route files named directly in #377810; more generally, any OmniAuth/OAuth callback handler or "continue"/"redirect_to" parameter that constructs its target from a route segment rather than an allowlisted, absolute, server-side-known destination.

**Potential bypass paths (unverified, falsifiable questions for a live instance):**
1. Do `config/routes/project.rb`'s `commit/:id` and `tree/*id` routes (or their current equivalents — route file layout may have changed since #377810) still prepend a slash to a decoded segment without passing it through a canonicalizing helper, on the current version?
2. Is there a **third** call site — added after 2022 — that decodes a path segment and builds a redirect/URL from it without reusing whatever helper (if any) generalized the `dvcs.rb` fix?
3. Does the fixed `dvcs.rb` substitution run *before* or *after* any other transformation that could reintroduce a leading `//` (e.g., a later `File.join`/route-prefix concatenation)?

**Candidate files/functions:** `lib/gitlab/jira/dvcs.rb` (confirm the fix is still exactly this narrow substitution, or whether it was later generalized); `config/routes/project.rb` and `config/routes/repository_deprecated.rb` (confirm current routing for `commit/:id`, `tree/*id`, `/refs/:id/logs_tree/*path` against the exact pattern #377810 described); `app/controllers/omniauth_callbacks_controller.rb` and `app/controllers/oauth/*` (never audited for this specific pattern in any source reviewed — candidate by architectural similarity only, not by a known historical hit).

**Reason candidate deserves manual validation:** GitLab's own engineers are on record, in a public issue, stating the original fix missed at least two sibling routes; there is no evidence any of these three locations were re-audited for the *general* class (vs. the two specific routes named) rather than patched piecemeal. A grep for `gsub(%r{\/{2,}}` across the current codebase (not completed in this pass) would immediately show whether the fix pattern was ever centralized into a shared helper — if it still exists only in `dvcs.rb`, every other path-building call site is an open question by construction.

## Entry 2 — Path traversal in uploads: three independent historical instances in the same subsystem, and the current Rack-level defense's exact, documented scope limits

This entry covers three related historical findings against the **uploads** subsystem specifically (distinct from the general `Gitlab::PathTraversal` helper covered in [SECURITY_INVARIANTS.md INV-02](SECURITY_INVARIANTS.md)), because reading the actual current fix revealed concrete, citable scope limits rather than a generic "could be incomplete" caveat.

**Original vulnerable paths (three distinct historical bugs, same subsystem):**
- **2020, HackerOne #827052** (`vakzz`, $1,000 bounty, GitLab tracking issue `gitlab-org/gitlab#212175`): `app/services/uploads_rewriter.rb`'s `MARKDOWN_PATTERN` regex (`%r{\!?\[.*?\]\(/uploads/(?<secret>[0-9a-f]{32})/(?<file>.*?)\)}`) extracted a `:file` capture group with **zero path validation**, then `find_file` → `FileUploader.new(...).retrieve_from_store!(file)` → `klass.copy_to(file, target_parent)` used that raw string directly when copying uploads during an **issue move between projects**. A markdown description of `![a](/uploads/1111.../../../../../../etc/passwd)` caused GitLab to copy `/etc/passwd` into the destination project's uploads, from where it could be read back over HTTP. The reporter additionally chained this to a **credential-theft-to-RCE** path: read `secrets.yml` for `secret_key_base` via the same traversal, then forge a Marshal-serialized Rails cookie (`cookies_serializer: :hybrid`) to achieve remote code execution.
- **2023, CVE-2023-2825** (GitLab issue `gitlab-org/gitlab#412371`): the HTTP-serving route `/:repo/uploads/:id/:file` allowed `:file` to traverse outward, with traversal depth tied to group-nesting depth (N+1 relationship) — [HISTORICAL_VULNERABILITY_MODEL.md Class 2.1](HISTORICAL_VULNERABILITY_MODEL.md).
- Both predate and postdate the Workhorse-JWT upload-*ingest* allowlist (`lib/uploaded_file.rb#allowed_path?`) described in [SYSTEM_CONTEXT.md §6](SYSTEM_CONTEXT.md) — that allowlist protects the *upload* direction only; both historical bugs here are on the *read/copy* direction, a structurally different code path.

**Fixed path — the current, general-purpose defense (read directly from source, `lib/gitlab/middleware/path_traversal_check.rb`, a Rack middleware added after CVE-2023-2825 per GitLab MRs `!81241` "Logs when potential path traversal attempt detected", `!123477` "Rack middleware for path traversal checks", and `!153078` "Rack path traversal: exclude search query parameters"):**
```ruby
def call(env)
  return @app.call(env) unless Feature.enabled?(:check_path_traversal_middleware, Feature.current_request)
  ...
  return @app.call(env) unless path_traversal_attempt?(request, log_params)
  ...
  REJECT_RESPONSE
end

def path_traversal_attempt?(request, log_params)
  original_fullpath = request.filtered_path
  exclude_query_parameters(request)
  decoded_fullpath = CGI.unescape(request.fullpath)
  Gitlab::PathTraversal.path_traversal?(decoded_fullpath, match_new_line: false)
end
```
with `EXCLUDED_QUERY_PARAM_NAMES = %w[search search_title search_query term name filter filter_projects note body commit_message content description]` stripped from the fullpath before the check runs, up to `NESTED_PARAMETERS_MAX_LEVEL = 5` of nested-hash recursion.

**Security invariant:** any path derived from user input, by any mechanism (HTTP route parameter, markdown-embedded reference, form field), must be canonicalized/validated before being used to read, copy, or write a file (see [SECURITY_INVARIANTS.md INV-02](SECURITY_INVARIANTS.md)).

**Patch mechanism:** a **request-level, feature-flagged Rack middleware** added as a defense-in-depth layer *in front of* the whole application, checking `request.fullpath` (URL path + query string) against the shared `Gitlab::PathTraversal` regex — a categorically different mechanism from either historical fix (the 2020 UploadsRewriter fix would have needed to validate the regex-captured `:file` group directly; the 2023 fix presumably added validation to the specific uploads-serving controller).

**Residual assumptions — stated precisely, from reading the actual code, not inferred generically:**
1. **This middleware inspects `request.fullpath` only — the URL and its query string. It never reads or checks the POST/PUT request body.** Any path-traversal-relevant value delivered as a JSON API body field, a multipart form field, or a GraphQL variable is **entirely outside this middleware's coverage** and depends solely on that specific endpoint calling `Gitlab::PathTraversal.check_path_traversal!` itself. The 2020 UploadsRewriter bug specifically was reachable via an **issue description** (a body field, submitted via a form or API), which this middleware — had it existed then — would **not** have caught, since it only looks at `fullpath`.
2. **A fixed, 12-name exclusion list (`EXCLUDED_QUERY_PARAM_NAMES`) is stripped from checking entirely**, and the comment says these names were excluded because "they are valid genuine requests" that happened to trip the regex — meaning **any of these exact parameter names, anywhere in the app, is permanently invisible to this middleware**, regardless of what that specific endpoint actually does with the parameter. `content`, `description`, `body`, and `note` are exactly the kind of free-text fields that historically carried the 2020 markdown-based payload; if any current or future feature builds a file path from a `content`/`description`/`body`/`note`-named parameter, this middleware provides zero protection for it by construction, not by oversight in a specific endpoint.
3. `match_new_line: false` is passed here, diverging from `Gitlab::PathTraversal.check_path_traversal!`'s own default (`match_new_line` defaults to `true` when called via the raising helper) — meaning a payload containing an embedded newline is checked less strictly at the middleware layer than at some direct call sites, an inconsistency between two enforcement points of what is supposed to be the same invariant.
4. The whole mechanism is gated by `Feature.enabled?(:check_path_traversal_middleware, ...)` — a feature flag that could be disabled instance-wide (by an admin, by a rollout regression, or by whatever default a self-managed install ships with) without that being obvious from application behavior in normal use.

**Sibling implementations:** the Workhorse-ingest allowlist (`lib/uploaded_file.rb`, [SYSTEM_CONTEXT.md §6](SYSTEM_CONTEXT.md)) — canonicalize-and-allowlist, applied only to uploads; the general `Gitlab::PathTraversal.check_path_traversal!` raising helper — applied ad hoc, per-endpoint, at the ~19 call sites enumerated in [SECURITY_INVARIANTS.md INV-02](SECURITY_INVARIANTS.md); this Rack middleware — regex-blocklist, URL/query-string only, with an explicit exemption list. **Three distinct enforcement mechanisms for one invariant**, each with a different, non-overlapping scope.

**Potential bypass paths (falsifiable questions):**
1. Does any current feature build a filesystem path (directly or via a service object like the historical `UploadsRewriter`) from a **request body** field, where the only traversal defense in the request path is this middleware (which never inspects the body) and the endpoint itself does not separately call `check_path_traversal!`?
2. Does any current feature build a filesystem path from a parameter literally named `content`, `description`, `body`, `note`, `search`, `term`, `name`, or `filter` — the exact exclusion list — where that parameter's value is used in a file operation rather than (as the exclusion comment implies) purely as free-text search/content?
3. Is `UploadsRewriter` (or its current-day equivalent for issue/MR move operations) now calling `Gitlab::PathTraversal.check_path_traversal!` on the `:file` capture group directly, independent of the Rack middleware — i.e., was the *specific* 2020 sink actually fixed at the sink, or only made harder to reach via the newer, differently-scoped middleware?

**Candidate files/functions:** `app/services/uploads_rewriter.rb` (or current equivalent — exact current path not confirmed in this pass; the historical file name may have moved) — the single highest-priority file to re-read in full, specifically checking whether `find_file`/the `:file` capture group is now validated at the point of use, independent of the Rack middleware; `lib/gitlab/middleware/path_traversal_check.rb` itself (fully read above); any controller/service using a parameter named from the `EXCLUDED_QUERY_PARAM_NAMES` list to construct a path.

**Reason candidate deserves manual validation:** this is not speculative pattern-matching — it is a **directly-read, current-code, documented scope boundary** (the exclusion list and the fullpath-only scope are explicit in the code, not inferred), on a subsystem with three confirmed historical hits (2020, 2023, and the still-active-as-of-2026 CVE-2026-85706 in a different route of the same general "serve a file by a path-shaped parameter" class per [THREAT_MODEL.md T1-A](THREAT_MODEL.md)). The question of whether the *specific* 2020 sink (`UploadsRewriter`) was ever fixed at the source, versus only gaining an additional, differently-scoped perimeter defense, was not resolved in this pass and is the most concrete, fastest-to-answer open question in this document.

## Entry 3 — ruby-saml parser differential: a vulnerability class that survived being "fixed" at least twice

**Original vulnerable path (CVE-2024-45409):** `lib/xml_security.rb` inside `ruby-saml` used REXML to extract `SignedInfo`/`SignatureValue` and Nokogiri to extract/canonicalize the assertion content whose `DigestValue` was checked — broad, non-relative XPath queries (`//ds:Reference`-shaped) let an attacker inject extra XML elements so the two parsers each validated/trusted a *different* element of the same document. Fixed in ruby-saml **1.18.0** by establishing a direct link between the hashed content, the digest, and the signature (per [GitHub Security Lab's writeup](https://github.blog/security/sign-in-as-anyone-bypassing-saml-sso-authentication-with-parser-differentials/), already cited in [HISTORICAL_VULNERABILITY_MODEL.md Class 8](HISTORICAL_VULNERABILITY_MODEL.md)).

**What that fix did NOT change (confirmed by two subsequent advisories against the same library):**
- **CVE-2025-25291/25292** (GHSA advisories, fixed in ruby-saml **1.18.0** — the search evidence is ambiguous on whether this was concurrent with or immediately after the 1.18.0 fix above; treat as a closely-related, possibly-overlapping disclosure rather than double-counting) — a **DOCTYPE-handling** parser differential: REXML and Nokogiri disagree on how a `<!DOCTYPE>` declaration affects subsequent parsing, which is a *different* mechanical trigger for the *same class* of bug (two parsers, one trust decision) that the 1.18.0 signature-linkage fix did not address, because that fix connected signature-to-digest-to-content but did not make REXML and Nokogiri agree on document *structure* in the presence of a DOCTYPE.
- **CVE-2025-66567 / GHSA-9v8j-x534-2fx3**, explicitly described by its own advisory as addressing **"an incomplete patch for CVE-2025-25292"** — a **namespace-handling** parser differential, CVSS 9.3, fixed in ruby-saml **1.18.0** per the advisory text retrieved (version numbering across these three advisories is confusingly overlapping in the secondary sources reviewed and should be treated as approximate, not exact, without reading the ruby-saml CHANGELOG directly) — i.e., GitHub's own advisory for this fix states in plain language that the *previous* fix was itself incomplete.

**Security invariant:** the XML node whose signature is cryptographically verified must be the same node whose content is later trusted (see [SECURITY_INVARIANTS.md INV-08](SECURITY_INVARIANTS.md)).

**Patch mechanism (across all three disclosures):** each fix addressed a **specific mechanical trigger** for parser disagreement (XPath breadth → DOCTYPE handling → namespace handling) rather than eliminating the underlying two-parser architecture itself; none of the three, per the sources reviewed, moved to a single-parser verification pipeline.

**Residual assumptions:** that enumerating and closing each specific way REXML and Nokogiri can be made to disagree is a *complete* strategy. The pattern of "incomplete patch for [previous CVE]" appearing in the advisory title itself, twice in a row, in the same library, is strong direct evidence that the underlying two-parser architecture is the actual root cause and that further disagreement mechanisms (encoding handling, comment/CDATA handling, entity expansion edge cases, XML namespace prefix redefinition beyond what CVE-2025-66567 covered) are plausible, undiscovered siblings — this is stated as a structural inference from the advisory pattern itself, not as a claim that a specific new bypass exists.

**Sibling implementations:** none found in GitLab's own first-party code performing this specific two-parser XML pattern (this is a vendored-gem issue); the closest **structural** sibling in GitLab's own code is [Entry 4 below](PATCH_ARCHAEOLOGY.md) (GraphQL multiplex: the query that is *validated* is not guaranteed to be the query that is *executed*) — a different mechanism, same abstract shape ("the thing checked and the thing acted upon can diverge").

**Potential bypass paths:** none asserted against ruby-saml's *current* release (1.18.0+) — no evidence was found of a fourth disclosure. The concrete, answerable question is purely a **version-currency** one: which exact `ruby-saml`/`omniauth-saml` patch version is pinned in the target instance's `Gemfile.lock`, compared against the fixed-version list across all three advisories (not just the first one).

**Candidate files/functions:** the target instance's `Gemfile.lock` entry for `ruby-saml`, `omniauth-saml`, and `rexml`; `app/controllers/omniauth_callbacks_controller.rb` as the consuming code (not itself expected to contain the bug, but the reachability confirmation point — i.e., confirm SAML SSO is actually enabled and reachable on the test instance before spending further effort here).

**Reason candidate deserves manual validation:** three advisories in roughly a year, two of them explicitly labeled as fixing an incomplete predecessor, is the strongest direct textual evidence in this entire research effort (not an inference — the GHSA title says it) that a patched vulnerability class was not actually closed by its first fix. Re-verifying the *current* pinned version against all three fixed-version thresholds (not just checking "is it above 1.18.0," since 1.18.0 itself was apparently later shown to be an incomplete fix for at least one of the follow-on issues, per the advisory text) is a fast, conclusive, non-speculative check.

## Entry 4 — GitLab's GraphQL version-filter feature: two 2026 CVEs in the same small module, one of them a textbook "validated-vs-executed object" divergence

**Original vulnerable path — CVE-2026-19478 (code injection, CVSS 9.4):** `lib/gitlab/graphql/version_filter/future_field_fallback.rb` — the `@gl_introduced(version:)` directive mechanism (used to let clients query fields from a future GitLab version without a hard schema error during rolling deploys) synthesized a `GraphQL::Schema::Field` for any unrecognized-but-tagged field name **without an explicit resolver**. In `graphql-ruby`, a field with no resolver falls back to calling a same-named method on the underlying Ruby object — so an attacker-chosen field name became an attacker-chosen **method call on a live server-side object** (per [OX Security's technical writeup](https://www.ox.security/blog/gitlab-graphql-cve-2026-19478-19650/), naming lines 14–36 of that exact file).

**Original vulnerable path — CVE-2026-19650 (CSRF via GET, CVSS 7.1):** `lib/gitlab/graphql/version_filter/introduced_tracer.rb` — the tracer that implements the above future-field filtering stored **shared, single-slot instance state** (`@original_query_document`, `@contain_future_fields` in the pre-fix version, per OX Security) rather than state keyed per-query. In a **multiplexed** (batched) GraphQL request containing multiple queries, one query's `parse` step could overwrite the shared state before a *different* query in the same batch reached its `validate`/`execute` step — so the document that was validated (and subjected to the CSRF-relevant "is this a mutation" check in `graphql_controller.rb`, per [SECURITY_INVARIANTS.md INV-05](SECURITY_INVARIANTS.md)) was not reliably the same document that was actually executed. This is precisely the general shape "the document a query is validated as is not the document it executes as" (OX Security's own phrasing) — enabling a benign-looking, GET-eligible first query in a batch to smuggle a mutating second query past CSRF/GET-method protections.

**Fixed path (read directly from current source, both files, in full, above):**
- `future_field_fallback.rb`: `fallback_field` now explicitly sets `resolver_class: Resolvers::NilResolver` — every synthesized future-field resolves to `nil` unconditionally; there is no longer a no-resolver fallback path that could dispatch to an arbitrary object method.
- `introduced_tracer.rb`: state is now `@introduced_tracer_data = {}.compare_by_identity`, a **hash keyed by the actual document object** (identity-keyed, not a single shared slot), populated in `#parse` and read back in `#validate`, `#analyze_query`, and `#execute_query` via `@introduced_tracer_data[query.document]` — each query in a multiplex batch now retrieves *its own* original document, not whichever document happened to be in a shared instance variable most recently.

**Security invariant:** (for CVE-2026-19478) a GraphQL field's resolution must never fall through to an implicit, attacker-influenced method dispatch on a server object — every field must have an explicit, intentional resolver; (for CVE-2026-19650) the object that a security-relevant check (CSRF/mutation-detection, authorization) is evaluated against must be the exact same object that is subsequently acted upon — no shared/mutable intermediate state may let two logically-distinct operations in a batch cross-contaminate.

**Patch mechanism:** CVE-2026-19478 — replace "no resolver" (implicit, dangerous default) with an explicit, safe default resolver (`NilResolver`). CVE-2026-19650 — replace single-slot shared mutable state with identity-keyed per-object state (`compare_by_identity` hash), directly fixing the check/act divergence rather than adding a perimeter check.

**Residual assumptions:**
- `NilResolver` (CVE-2026-19478's fix) makes *unrecognized future fields* safely inert, but the fix is scoped specifically to fields that don't yet exist in the schema (the rolling-deploy compatibility mechanism). It does not, by itself, say anything about whether an *existing, recognized* field elsewhere in the schema could still resolve via a similar implicit-method-dispatch default if it lacks an explicit resolver for an unrelated reason (e.g., a newly-added field that a developer forgets to give a resolver, outside the `@gl_introduced` mechanism entirely) — `graphql-ruby`'s general behavior (call a same-named method when no resolver is defined) is a **library-level default**, and this fix only neutralizes the one code path (`FutureFieldFallback`) that was synthesizing fields from attacker-controlled names; it does not change the underlying `graphql-ruby` default itself for hand-authored schema fields.
- `introduced_tracer.rb`'s fix correctly scopes state by document identity, but depends on `query.document` being a stable, unique-per-query object reference throughout the tracer lifecycle (`parse` → `validate` → `analyze_query` → `execute_query`) — if any *other* part of the GraphQL execution pipeline replaces or duplicates a document object between these hook calls (for a reason unrelated to this specific filter), the identity-keyed lookup would silently miss (`doc_data` would be `nil`, `return result unless doc_data` / `return unless doc_data`), which fails safe for *this* filter's own logic (no fallback filtering applied) but is worth noting as a "fails to a different, not-obviously-worse state" rather than "fails to a provably safe state" — the code doesn't distinguish "this document deliberately has no future fields" from "this document's identity was lost due to an unrelated pipeline change."

**Sibling implementations:** the `graphql-ruby` no-resolver-implicit-method-dispatch default is a **library-wide** behavior, not specific to `FutureFieldFallback` — any other GitLab-authored code that dynamically constructs `GraphQL::Schema::Field` instances (rather than declaring fields statically in a `Types::*` class, which is the normal, safe pattern per [SYSTEM_CONTEXT.md §1](SYSTEM_CONTEXT.md)) is a structural sibling of CVE-2026-19478's root cause. The shared-mutable-tracer-state pattern (CVE-2026-19650) is structurally the same class of bug as any other GraphQL tracer/instrumentation module that keeps `@instance_variable` state across what might be multiple queries in one multiplexed request — `GitlabSchema` (per [SYSTEM_CONTEXT.md §3](SYSTEM_CONTEXT.md)) registers several tracers (`InstrumentationTracer`, `VersionFilter::IntroducedTracer`, plus subscription-related tracing) via `trace_with`, and any of the *other* registered tracers is a candidate for the identical "shared state across a multiplex batch" mistake unless it was independently designed to be per-query-keyed from the start.

**Potential bypass paths (falsifiable questions):**
1. Does any other GitLab-authored code (outside `FutureFieldFallback`) dynamically build a `GraphQL::Schema::Field` without an explicit `resolver_class`, `resolve`, or `method:` — i.e., does the *general* graphql-ruby implicit-dispatch default remain reachable through any other dynamic-field-construction code path GitLab has written? (Not searched in this pass — `app/graphql` was sparse-checked-out but a targeted grep for `GraphQL::Schema::Field.new` outside the fixed file was not run.)
2. Do any of `GitlabSchema`'s *other* registered tracers (`app/graphql/gitlab_schema.rb`'s `trace_with` list, read during [SYSTEM_CONTEXT.md](SYSTEM_CONTEXT.md) research: `InstrumentationTracer`, `VersionFilter::IntroducedTracer`, plus the subscriptions tracer) hold any `@instance_variable` state that is written in one trace hook and read in a later one, without being identity-keyed per query/document the way the fixed `introduced_tracer.rb` now is?
3. Is `NilResolver` itself a shared, stateless singleton-style resolver (safe by construction), or could it, in some code path, be parameterized/subclassed in a way that reintroduces object-method dispatch?

**Candidate files/functions:** `app/graphql/gitlab_schema.rb` (`trace_with` declarations — enumerate every registered tracer and check each for shared mutable state); any file under `app/graphql/` or `lib/gitlab/graphql/` constructing `GraphQL::Schema::Field.new` dynamically (not yet enumerated); `lib/gitlab/graphql/version_filter/future_field_filter.rb` (referenced by both fixed files as the class that actually determines `contain_future_fields`/`future_field_names` — read in this pass only by reference, not directly, and is the logical next file to read in full).

**Reason candidate deserves manual validation:** this is the single most concrete, most recently-fixed pair of entries in this document — both vulnerable *and* fixed code were read directly from primary/near-primary sources (a detailed third-party technical writeup naming exact line ranges, cross-checked against the current, live source tree), and the fix pattern for CVE-2026-19650 (identity-keyed per-query state replacing shared instance state) is a **general defensive pattern**, not a one-off patch — meaning its *absence* elsewhere (in the other registered tracers) is a precise, checkable question rather than a vague architectural worry.

## Entry 5 — Oj gem: a bounds check present in one sibling function, absent in another, within the same file

**Original vulnerable path:** the Oj gem's C extension, `ext/oj/fast.c`, function `doc_each_child` — when recursively invoked over deeply-nested JSON, incremented `doc->where` (a stack-array index) past the bound of a fixed-size `where_path[MAX_STACK = 100]` array with **no bounds check**, and never restored (`doc->where--`) the index after the loop — a stack buffer overflow reachable purely from untrusted, deeply-nested JSON input, no different in kind from the separate `Oj::Parser` OOB-write chain already covered in [HISTORICAL_VULNERABILITY_MODEL.md Class 7](HISTORICAL_VULNERABILITY_MODEL.md) (which GitLab reaches via `ipynbdiff`), but a **distinct function, distinct CVE** (CVE-2026-54592 / GHSA-3m6q-jj5j-38c9) in the same gem, same general "walk a JSON document tree" subsystem.

**Fixed path (Oj 3.17.3):** `doc_each_child` now bounds-checks `doc->where` before incrementing (raising a Ruby-level `Oj::DepthError` instead of overflowing the native stack buffer) and correctly restores `doc->where` after the loop — **explicitly matching the pattern that the sibling function `doc_each_leaf` already implemented**, per the fix description found. In other words: the correct, safe pattern already existed once in this file, in a function that does structurally the same kind of tree-walk, and was simply not applied to its sibling.

**Security invariant:** every size/depth/index field derived from untrusted input and used to address a fixed-size native buffer is bounds-checked before use, consistently across every function that walks the same data structure (see [SECURITY_INVARIANTS.md INV-07](SECURITY_INVARIANTS.md)).

**Patch mechanism:** add the missing bounds check and restore step to `doc_each_child`, bringing it in line with `doc_each_leaf`'s pre-existing, correct implementation of the same invariant.

**Residual assumptions:** that `doc_each_leaf` and `doc_each_child` are the *only two* tree-walking functions in `ext/oj/fast.c`/the broader Oj C extension that manipulate `doc->where` (or an equivalent stack-depth index) against a fixed-size array. The fact that one of exactly two closely-related functions had the check and the other didn't, for what appears to have been an extended period, is direct evidence that "does this sibling function apply the same bounds check as its neighbor" is not a rhetorical question in this codebase — it has already been answered "no" once.

**Sibling implementations:** any other `doc_each_*`/tree-traversal function in Oj's C source operating on `doc->where` or a similarly-purposed fixed-size stack array (not individually enumerated here — this would require reading the full `ext/oj/fast.c` source, not available in this pass's checkout since Oj is a separate vendored gem, not part of the `gitlab-org/gitlab` sparse checkout).

**Potential bypass paths:** none asserted against the *current*, patched Oj version. The concrete, falsifiable question is again a **version-currency** one, narrower than Entry 3's: is the pinned `oj` version ≥ 3.17.3 (fixing the `Oj::Parser`-based RCE chain in [HISTORICAL_VULNERABILITY_MODEL.md Class 7](HISTORICAL_VULNERABILITY_MODEL.md)) *and* does it also include the `doc_each_child` fix specifically (CVE-2026-54592) — these were found via separate advisories in this research and may not have shipped in the same Oj release; both fixed-version thresholds should be checked independently against the instance's `Gemfile.lock`, not assumed to be the same line.

**Candidate files/functions:** the target instance's `Gemfile.lock` pin for `oj`; every GitLab call site of `Oj::Doc` (as opposed to `Oj::Parser`, which is the specific API `ipynbdiff` uses per [HISTORICAL_VULNERABILITY_MODEL.md Class 7](HISTORICAL_VULNERABILITY_MODEL.md)) — not enumerated in this pass; `Oj::Doc` is a different entry point into the same gem and its GitLab call sites (if any) were not searched for.

**Reason candidate deserves manual validation:** this is a directly-documented instance of "the fix for a sibling function was not applied uniformly" — exactly the failure mode [SECURITY_INVARIANTS.md](SECURITY_INVARIANTS.md) predicted architecturally for GitLab's own code, found instead in a dependency GitLab's own RCE chain (Entry-adjacent, Class 7) already implicates. It reinforces that "check every sibling of a fixed function, in the same file, for the same missing check" is a productive, non-hypothetical technique against this specific dependency, and by extension against GitLab's own code wherever a similar closely-related-function-pair pattern exists (a generalizable technique, not just a fact about Oj).

## Cross-entry pattern: "the thing checked is not reliably the thing acted upon"

Three of the five entries above — Entry 3 (ruby-saml: signature verified on one parser's view, content trusted from another's), Entry 4/CVE-2026-19650 (GraphQL: document validated is not guaranteed to be the document executed, before the fix), and [SECURITY_INVARIANTS.md INV-03](SECURITY_INVARIANTS.md)'s CI/CD pipeline-identity entries (authorization decided about one state, acted on a possibly-different state) — are the **same abstract invariant** ("verification target == consumption target, atomically, with no intervening opportunity for the two to diverge") manifesting in three unrelated subsystems (XML signature verification, GraphQL batch execution, CI/CD pipeline authorization). This cross-cutting recurrence, found only by doing the archaeology rather than reading each historical bug in isolation, is the strongest single piece of evidence in this document for where a *novel* (not-yet-disclosed) instance of the same abstract flaw is most likely to be found next: **any code that separates a "decide" step from an "act" step via intermediate mutable state (an instance variable, a cache entry, a re-resolved reference) rather than closing over the decided-upon object/value directly.** A systematic grep for `@`-prefixed instance variables written in one method and read in a differently-timed callback/hook across `app/graphql/`, `lib/gitlab/auth/`, and the CI/CD pipeline services would be the concrete next research step suggested by this pattern, and was not completed in this pass due to time budget.
